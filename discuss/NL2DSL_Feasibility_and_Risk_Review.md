# NL2DSL 方案可行性与风险评估报告

**日期**: 2025-12-15
**状态**: 正式评审 (Formal Review)
**范围**: 针对 `Architecture_Analysis_NL2SQL_vs_NL2DSL.md` 和 `NL2DSL_Implementation_Roadmap.md` 两份文档进行客观分析

---

## 一、总体评价

两份文档整体思路**方向正确**，识别出了 Vanna (NL2SQL) 在企业级落地时面临的核心问题（幻觉、一致性、安全）。提出的 NL2DSL + Semantic Layer 方案在理论上**具有可行性**，但在实施层面存在**若干被低估的挑战和风险**。

---

## 二、可行性分析

### 2.1 技术可行性 ✅

| 模块 | 可行性 | 说明 |
| :--- | :---: | :--- |
| **JSON Schema DSL** | 高 | 业界标准实践。Schema 校验 (Pydantic/JSON Schema) + LLM Function Calling 已成熟。 |
| **Python Compiler (DSL → SQL)** | 高 | 使用 `SQLAlchemy Core` 或 `SqlGlot` 可避免字符串拼接，且天然支持方言适配。 |
| **Metrics Store (YAML)** | 高 | 概念成熟，可参考 dbt Metrics / Cube.js / Lightdash 的设计。 |
| **Join Graph (自动推断)** | 中 | 理论可行，但需要精确的元数据（Foreign Key）。许多数仓（尤其是宽表模型）不显式定义 FK，需要人工录入。 |
| **权限注入 (RLS/CLS)** | 中 | 技术可行，但需要与现有身份认证系统深度集成（用户角色 → 权限策略 → SQL 改写）。 |

### 2.2 业务可行性 ⚠️ (部分风险)

| 维度 | 评估 | 说明 |
| :--- | :---: | :--- |
| **指标定义** | 中 | 企业内部往往存在"同一个词、不同定义"（如财务 GMV vs 运营 GMV）。需要跨部门协作敲定语义。 |
| **术语归一化** | 中 | 需要业务方配合梳理同义词。这是**组织工作**而非纯技术工作。 |
| **用户接受度** | 中 | 分析师可能抗拒"我说的话，要经过一个 JSON 中转"。需要良好的 UI 解释透明度。 |

## 三、风险识别

### 3.1 🔴 关键风险 (High)

#### R1: DSL 表达力不足导致覆盖率低
*   **描述**: 如果 DSL 设计过于简单（只覆盖 Filter, Group By, Aggregate），遇到真实业务场景（窗口函数、CTE、条件聚合）时无法表达，用户会逃逸回 NL2SQL，架构形同虚设。
*   **影响**: 方案无法替代 NL2SQL，沦为"玩具"。
*   **缓解措施**:
    *   先调研 Top 100 历史 SQL，统计算子分布，确保 DSL 覆盖 80%+ 的高频模式。
    *   为复杂查询预留 `raw_sql_fragment` 逃生舱，但需审计留痕。

#### R2: Metrics Store 与实际数仓严重脱节
*   **描述**: 业务指标定义在 YAML 里写的是 `sum(order_amount)`，但数仓实际改成了 `sum(final_amount)`，导致数据对不上。
*   **影响**: 信任度崩塌，用户不再使用系统。
*   **缓解措施**:
    *   建立元数据同步的 CI/CD 流程（Schema Drift Detection）。
    *   为 Metrics 定义添加 `last_verified_at` 字段，设置校验 SLA。

### 3.2 🟡 中等风险 (Medium)

#### R3: LLM 生成 DSL 准确率不及预期
*   **描述**: 文档假设 LLM 更容易生成 JSON 而非 SQL。这在**简单场景**成立，但当用户的自然语言本身含糊（如"上个月"是"自然月"还是"最近 30 天"？），LLM 仍然会幻觉。
*   **缓解措施**:
    *   在 DSL 中设计 `assumptions` 字段，让 LLM 显式声明其假设。
    *   增加澄清轮次（Clarification Round）而非直接生成。

#### R4: 编译器工程量被低估
*   **描述**: "Week 1-4 跑通 MVP" 过于乐观。仅考虑 Aggregation + Filter，若加上 Join 推断、多方言支持、权限注入，工作量可能翻 3~5 倍。
*   **缓解措施**:
    *   明确 MVP 范围：**单表 + 无 Join + PostgreSQL Only**。
    *   后续分阶段扩展，每个阶段有独立交付物。

### 3.3 🟢 低风险 (Low)

#### R5: Vanna 改造成本
*   **描述**: 修改 Vanna Prompt 让其输出 JSON 而非 SQL。
*   **评估**: 本质是 Prompt Engineering，风险可控。可通过 `Few-Shot + JSON Mode / Function Calling` 快速实现。

## 四、遗漏与建议补充

### 4.1 文档遗漏项

| 遗漏项 | 重要性 | 建议 |
| :--- | :---: | :--- |
| **错误处理策略** | 高 | 当 Compiler 编译失败时，返回什么给用户？需要定义用户友好的错误分类。 |
| **多轮对话状态** | 高 | DSL 是单轮还是多轮？如何支持"基于上一轮结果再筛选"？ |
| **性能基线** | 中 | NL2DSL 增加了编译层，端到端延迟增加多少？需要 Benchmark。 |
| **版本管理** | 中 | DSL Schema 升级时如何处理历史数据的兼容性？ |
| **Fallback 机制** | 中 | 当 DSL 无法表达时，是否允许降级到 NL2SQL？如何审计？ |

### 4.2 建议增补的实施细节

1.  **定义 MVP 验收标准**: 文档中缺乏可量化的成功指标。建议增加：
    *   DSL 生成准确率 > 85%
    *   编译成功率 > 95%
    *   端到端延迟 < 3s

2.  **测试策略**: 文档未提及如何测试编译器。建议：
    *   单元测试：DSL JSON → SQL 的黄金样例库
    *   集成测试：SQL 执行结果与 Ground Truth 对比

3.  **可观测性**: 建议增加对编译层的监控：
    *   DSL 命中率（LLM 生成的 DSL 编译成功的比例）
    *   指标调用分布（哪个 Metric 被调用最多）
    *   错误分类统计

## 五、结论与建议

### ✅ 优点
1.  方向正确，抓住了 NL2SQL 的核心痛点（幻觉 + 不一致）。
2.  渐进式路线图设计合理（MVP → 语义层 → 治理）。
3.  复用 Vanna 而非重写，降低了技术风险。

### ⚠️ 需改进
1.  **时间估计过于乐观**：建议将 Week 1-4 的 MVP 拆为 2 个 Sprint，各 2 周，含 Buffer。
2.  **DSL 表达力需验证**：在启动编码前，先用历史 SQL 做覆盖率分析。
3.  **业务协作未提及**：元数据治理是"人+系统"共同完成的，建议增加相关沟通计划。

| 优先级 | 行动项 | 负责方 |
| :---: | :--- | :--- |
| P0 | 调研 Top 100 历史 SQL，确定 DSL 算子最小集 | 技术 + 数据团队 |
